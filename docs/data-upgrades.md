# Перенос данных между версиями

Версия приложения (`0.2.0`) и версия структуры данных (`PRAGMA user_version`,
сейчас `5`) независимы: выпуск приложения без изменения таблиц не требует
новой миграции. Номер версии данных увеличивается при изменении схемы.

## Обычное обновление

Демон при открытии writable-базы вызывает существующий `migrate`.
GUI с read-only-подключением миграции не выполняет.
Перед изменениями проверяется целостность SQLite и создаётся резервная копия
`<имя БД>.<время UTC>.bak` через SQLite backup API, включая WAL.
Копия создаётся и для баз, содержащих только сотрудников или МЧД.
Изменения проходят в транзакции `BEGIN IMMEDIATE`; при ошибке она откатывается.
Версия данных меняется только после успешной проверки целостности.

Поддерживаются существующие переходы:

| Версия | Преобразование |
|---|---|
| 0 → 1 | Контакты и поисковые данные сертификатов |
| 1 → 2 | Должность, ИНН, СНИЛС и дата рождения сотрудников |
| 2 → 3 | Метаданные файлов-источников и журнал аудита |
| 3 → 4 | Нормализованный список полномочий МЧД |
| 4 → 5 | Признак руководства у сотрудника |

Версия 0 означает старую БД без явной отметки версии. Поддерживаются форматы,
для которых есть описанные миграции; произвольные сторонние базы не принимаются.
База новее программы отклоняется без обратного преобразования.

## Преобразование отдельной копии

`infrastructure/database/data_upgrade.py` предоставляет
`upgrade_database_copy(source, destination)`. Это отдельный API для
подготовки данных, без новых кнопок GUI или прямой записи GUI в базу.

```python
from pathlib import Path
from certificate_analyzer.infrastructure.database.data_upgrade import upgrade_database_copy

result = upgrade_database_copy(Path("old.db"), Path("upgraded.db"))
print(result.source_version, result.target_version, result.database_path)
```

Исходная БД сохраняется. Работа выполняется во временной копии, затем
проверяются целостность и отсутствие уменьшения числа существующих записей.
Добавляются отсутствующие таблицы актуальной модели. Результат публикуется
целиком без перезаписи существующего целевого файла. Нужна файловая система,
поддерживающая hard links; при отсутствии поддержки операция завершается ошибкой.
Остановите демон и закройте пользователей БД до переключения на новую копию.
Проверка IPC-токена не заменяет блокировку от конкурентного запуска.

## Импорт старого защищённого архива

Импорт архива версии 1 теперь принимает старую поддерживаемую схему БД.
После расшифрования миграция выполняется в staging-копии **до** публикации
нового профиля и замены путей. Исходный архив и текущий профиль не меняются.
Более новая схема вызывает понятную ошибку с предложением обновить программу.
Формат упаковки архива остаётся версии 1; его будущие версии требуют отдельного
преобразования manifest, которого пока нет.

Механизм работает с обычной SQLite. SQLCipher требует отдельного подключения
миграций через его драйвер и ключ; автоматически здесь не используется.

## Добавление следующей версии

Добавьте следующий переход в `migrations.py`, затем увеличьте `SCHEMA_VERSION`.
Проверьте обновление старых БД с данными, повторный запуск, откат при ошибке,
сохранность резервной копии и импорт архива предыдущей схемы. Не связывайте
номер схемы напрямую с номером релиза и не изменяйте ранее выпущенные переходы
так, чтобы результат зависел от версии программы, выполнившей миграцию.
